\subsection{Case Study: Übersetzung des Notebooks 04-CNF}
Das vorliegende Notebook \href{https://github.com/zLeoll/TS-Translation-for-TheoInf/blob/main/Logic/Chapter-4/04-CNF.ipynb}{04-CNF.ipynb} demonstriert die Überführung von aussagenlogischen Formeln in die \ac{KNF}. Anhand dieser Case Study werden die grundlegenden Unterschiede zwischen Python und TypeScript in Bezug auf Typisierung, Datenstrukturen und Kontrollfluss veranschaulicht.




Zunächst werden der \texttt{LogicParser} sowie spezielle Datenstrukturen aus der Bibliothek \texttt{recursive-set} importiert:
\Needspace{7\baselineskip}
\begin{minted}{typescript}
 import { LogicParser } from './PropositionalLogicParser';
 import { RecursiveSet, Tuple } from 'recursive-set';
\end{minted}
\captionof{listing}{ Importieren des Parsers und recurisve-set}


Ein Parser ist in diesem Kontext zwingend erforderlich, da die aussagenlogischen Formeln zunächst als einfache Strings vorliegen (bspw. $(p \land q) \rightarrow r$) und erst in eine strukturierte, maschinenlesbare Form, wie einen abstrakten Syntaxbaum, überführt werden müssen, bevor die anschließenden algorithmischen Transformationen zur \ac{KNF} auf sie angewendet werden können. Die Python-Version bindet den Parser stattdessen komfortabel per \texttt{\%run Propositional-Logic-Parser.ipynb} ein ohne zusätzliche Bibliothek. 
Dies markiert einen der fundamentalsten Unterschiede zur Python-Welt: Während Python für herkömmliche Tupel (\texttt{tuple}) und unveränderliche Mengen (\texttt{frozenset}) standardmäßig eine inhaltliche Wertgleichheit überprüft, vergleicht TypeScript Objekte und Arrays lediglich über ihre Speicherreferenz. Zwei Arrays mit den exakt gleichen Inhalten gelten demnach als ungleich, wenn sie nicht denselben Speicherbereich belegen. Um das Verhalten von Pythons \texttt{frozenset} in TypeScript nachzubilden, muss zwingend auf die Bibliothek \texttt{recursive-set} zurückgegriffen werden, welche die Klassen \texttt{RecursiveSet} und \texttt{Tuple} bereitstellt.







\subsubsection{Typdefinitionen in Python vs.\ TypeScript (präziser Vergleich)}
Die Typdefinitionen in beiden Implementierungen verfolgen das gleiche fachliche Ziel (Formel, Literal, Klausel, \ac{KNF}), unterscheiden sich jedoch grundlegend in ihrer \textit{Präzision} und damit in der Fähigkeit, fehlerhafte Strukturen frühzeitig auszuschließen. In Python dienen die Annotationen primär der Dokumentation und optionaler statischer Analyse, während TypeScript die zulässige Struktur des Syntaxbaums und der Mengenkonstrukte deutlich enger über Union-Typen und fest geformte Tupel beschreibt.

\Needspace{7\baselineskip}
\begin{minted}{python}
	Variable = str
	Formula  = TypeVar('Formula')
	Formula  = Variable | tuple[Formula, ...]
	Literal  = Variable | tuple[str, Variable]
	Clause   = frozenset[Literal]
	CNF      = set[Clause]
\end{minted}
\captionof{listing}{Python: Typalias-Set für Variablen, Formeln, Literale, Klauseln und \ac{KNF}}

\Needspace{7\baselineskip}
\begin{minted}{typescript}
	type Variable = string;
	type Formula  =
	| Variable
	| ['⊤' | '⊥']
	| ['¬', Formula]
	| ['↔' | '→' | '∧' | '∨', Formula, Formula];
	
	type Literal  = Variable | Tuple<['¬', Variable]>;
	type Clause   = RecursiveSet<Literal>;
	type CNF      = RecursiveSet<Clause>;
\end{minted}
\captionof{listing}{TypeScript: Strukturell präzise Union-Typen und wertbasierte Mengen über \texttt{recursive-set}}

\paragraph{Formel-Typ (\texttt{Formula}).}
In Python ist \texttt{Formula} sehr allgemein als „Variable oder beliebiges Tupel rekursiver Formeln“ modelliert (\texttt{tuple[Formula, ...]}). Dadurch lässt sich zwar jede baumartige Repräsentation typisieren, jedoch werden weder die erlaubten Operatoren noch die korrekte Stelligkeit (z.\,B. binär für \(\land\), \(\lor\), \(\to\), \(\leftrightarrow\)) durch den Typ erzwungen.

\Needspace{7\baselineskip}
\begin{minted}{python}
	# Typisch gemeint (binärer Operator):
	f1: Formula = ('∧', 'p', 'q')
	
	# Wird vom Typ ebenfalls akzeptiert, ist aber strukturell fehlerhaft:
	f2: Formula = ('∧', 'p')              # falsche Stelligkeit
	f3: Formula = ('XOR', 'p', 'q')       # Operator nicht vorgesehen
	f4: Formula = ('¬', ('∧', 'p', 'q'))  # ebenfalls möglich
\end{minted}
\captionof{listing}{Python: \texttt{Formula} ist flexibel, aber typseitig kaum restriktiv}

TypeScript beschreibt \texttt{Formula} dagegen als Union aus exakt vier Formen: Variable, Wahrheitskonstante, Negation mit genau einem Operand, sowie binärer Operator mit genau zwei Operanden. Damit wird die Stelligkeit direkt im Typ festgelegt; zudem sind die Operator-Symbole explizit enumeriert.

\Needspace{7\baselineskip}
\begin{minted}{typescript}
	const f1: Formula = ['∧', 'p', 'q'];             // gültig
	const f2: Formula = ['¬', ['∨', 'p', 'q']];      // gültig
	
	// Strukturelle Fehler würden hier bereits durch den Typ auffallen:
	// const bad1: Formula = ['∧', 'p'];            // falsche Stelligkeit
	// const bad2: Formula = ['XOR', 'p', 'q'];     // Operator nicht erlaubt
\end{minted}
\captionof{listing}{TypeScript: \texttt{Formula} erzwingt Operator-Menge und Stelligkeit über Union-Typen}

\paragraph{Literal-Typ (\texttt{Literal}).}
In Python ist ein Literal entweder eine Variable (\texttt{str}) oder ein Tupel \texttt{tuple[str, Variable]}. Diese Definition ist bewusst knapp, aber sie lässt (rein vom Typ her) auch ungültige Konstruktionen zu, da das erste Tupel-Element nur als \texttt{str} und nicht als festes Symbol \texttt{'¬'} beschrieben ist.

\Needspace{7\baselineskip}
\begin{minted}{python}
	l1: Literal = 'p'          # positives Literal
	l2: Literal = ('¬', 'p')   # negatives Literal (intendiert)
	
	# Typseitig ebenfalls möglich, semantisch jedoch falsch:
	l3: Literal = ('not', 'p')
	l4: Literal = ('∧', 'p')
\end{minted}
\captionof{listing}{Python: \texttt{Literal} ist typseitig zu allgemein für das Negationssymbol}

In TypeScript wird das negative Literal als \texttt{Tuple<['¬', Variable]>} modelliert. Hierzu ist eine kurze Ergänzung notwendig: Ein Ausdruck der Form \texttt{X<...>} ist eine \textit{Parametrisierung} eines Typs (vergleichbar mit „der Typ \texttt{X} mit genau diesen Inhaltstypen“). Dadurch ist festgelegt, dass das Tupel exakt die Form \([\texttt{'¬'}, \texttt{Variable}]\) besitzt, wodurch „falsche Operator-Tupel“ bereits auf Typ-Ebene verhindert werden.

\Needspace{7\baselineskip}
\begin{minted}{typescript}
	const l1: Literal = 'p';
	const l2: Literal = new Tuple('¬', 'p');
	
	// Strukturell falsche Literale wären nicht mit dem Typ vereinbar:
	// const bad: Literal = new Tuple('not', 'p');
\end{minted}
\captionof{listing}{TypeScript: Negierte Literale sind als Tupel mit festem Präfix \texttt{'¬'} typisiert}

\paragraph{Klauseln und \ac{KNF}: \texttt{frozenset}/\texttt{set} vs.\ \texttt{RecursiveSet}.}
Python nutzt \texttt{frozenset[Literal]} für Klauseln (unveränderliche Menge) und \texttt{set[Clause]} für die \ac{KNF} (Menge von Klauseln). Die Unveränderlichkeit der Klausel ist entscheidend, weil nur unveränderliche Objekte in Python als Elemente einer äußeren Menge auftreten können (eine \texttt{set} kann keine \texttt{set} enthalten, ein \texttt{frozenset} jedoch schon).

\Needspace{7\baselineskip}
\begin{minted}{python}
	C1: Clause = frozenset({'p', ('¬', 'q')})
	C2: Clause = frozenset({('¬', 'q'), 'p'})   # gleiche Inhalte wie C1
	
	S: CNF = {C1, C2}  # enthält typischerweise nur ein Element, da C1 == C2
\end{minted}
\captionof{listing}{Python: \texttt{frozenset} ermöglicht Mengen-von-Mengen mit Wertgleichheit}

In TypeScript sind Arrays/Objekte standardmäßig referenzbasiert, weshalb für eine mengenartige Repräsentation mit Wertgleichheit eine spezielle Bibliothek erforderlich ist. \texttt{RecursiveSet} und \texttt{Tuple} übernehmen hierbei die Rolle von \texttt{set}/\texttt{frozenset} inklusive struktureller Gleichheit auch für verschachtelte Elemente (z.\,B. Literale als Tupel), sodass \ac{KNF}-Mengenoperationen zuverlässig auf Inhalte statt auf Speicherreferenzen reagieren.

\Needspace{7\baselineskip}
\begin{minted}{typescript}
	const C1: Clause = new RecursiveSet<Literal>([
	'p',
	new Tuple('¬', 'q'),
	]);
	
	const C2: Clause = new RecursiveSet<Literal>([
	new Tuple('¬', 'q'),
	'p',
	]);
	
	const S: CNF = new RecursiveSet<Clause>([C1, C2]); // soll C1 und C2 als gleich erkennen
\end{minted}
\captionof{listing}{TypeScript: \texttt{RecursiveSet} als Ersatz für \texttt{frozenset}/\texttt{set} bei wertbasierter Gleichheit}




Ein besonderes Merkmal der TypeScript-Version ist das iterative Einschränken des Typensystems (sogenanntes Type Narrowing). Im folgenden werden spezifischere Formel-Typen deklariert (\texttt{Formula1}, \texttt{Formula2} und \texttt{NNF}), bei denen sukzessive Operatoren wie \texttt{'↔'} und \texttt{'→'} aus dem Union-Typ entfernt werden. Dies erhöht die statische Typsicherheit in den nachfolgenden Transformationsschritten signifikant, während Python für alle Zwischenzustände durchgehend denselben \texttt{Formula}-Typ verwendet.

\Needspace{7\baselineskip}
\begin{minted}{typescript}
 type Formula1 = Variable | ['⊤' | '⊥'] | ['¬', Formula1] | 
                 ['→' | '∧' | '∨', Formula1, Formula1];
 type Formula2 = Variable | ['⊤' | '⊥'] | ['¬', Formula2] | 
                 ['∧' | '∨', Formula2, Formula2];
 type NNF =      Variable | ['⊤'] | ['⊥'] | ['¬', Variable] | 
                 ['∧' | '∨', NNF, NNF];
\end{minted}
\captionof{listing}{Iteratives Type Narrowing der Formeln}


\subsubsection{Eliminierung von \texttt{↔} im Vergleich: Python vs.\ TypeScript}
Die Funktionen \texttt{eliminateBiconditional} und \texttt{eliminateConditional} markieren den Übergang von einer allgemeinen Formelrepräsentation hin zu einer strukturell eingeschränkten Zwischenform, in der die Operatoren '↔' und '→' nicht mehr auftreten. 
In der TypeScript-Version wird dieser Schritt nicht nur algorithmisch, sondern zusätzlich \textit{typseitig} abgesichert: \texttt{eliminateBiconditional} liefert den engeren Typ \texttt{Formula1} (ohne \texttt{↔}), während Python für alle Zwischenzustände durchgehend denselben \texttt{Formula}-Typ verwendet.

\Needspace{7\baselineskip}
\begin{minted}{python}
	def eliminateBiconditional(f: Formula) -> Formula:
	'Eliminate the logical operator "↔" from the formula f.'
	match f:
	case str(p):        # This case covers variables.
	return p
	case ('↔', g, h):
	return eliminateBiconditional(('∧', ('→', g, h), ('→', h, g)))
	case ('⊤', ) | ('⊥', ):
	return f
	case ('¬', g):
	return ('¬', eliminateBiconditional(g))
	case (op, g, h):    # This case covers '→', '∧', and '∨'.
	return (op, eliminateBiconditional(g), eliminateBiconditional(h))
	return None # type: ignore
\end{minted}
\captionof{listing}{Python: \texttt{eliminateBiconditional} mit Pattern Matching und einheitlichem \texttt{Formula}-Typ}

\Needspace{7\baselineskip}
\begin{minted}{typescript}
	export type Formula1 =
	| Variable
	| ['⊤' | '⊥']
	| ['¬', Formula1]
	| ['→' | '∧' | '∨', Formula1, Formula1];
	
	export function eliminateBiconditional(f: Formula): Formula1 {
		'Eliminate the logical operator "↔" from f.'
		if (typeof f === 'string') {
			return f;
		}
		
		const [op] = f;
		switch (op) {
			case '↔': {
				const [, g, h] = f;
				return eliminateBiconditional(['∧', ['→', g, h], ['→', h, g]]);
			}
			case '⊤':
			return ['⊤'];
			case '⊥':
			return ['⊥'];
			case '¬': {
				const [, g] = f;
				return ['¬', eliminateBiconditional(g)];
			}
			case '→':
			case '∧':
			case '∨': {
				const [, g, h] = f;
				return [op, eliminateBiconditional(g), eliminateBiconditional(h)];
			}
		}
	}
\end{minted}
\captionof{listing}{TypeScript: \texttt{eliminateBiconditional} mit Type Guards und Rückgabetyp \texttt{Formula1} (ohne \texttt{↔})}

\paragraph{Begriffsklärung: Type Guard und Type Narrowing.}
Ein \textit{Type Guard} ist in TypeScript eine Laufzeitprüfung, die dem Compiler gleichzeitig als Hinweis dient, einen Union-Typ in einem Kontrollflusszweig auf einen spezifischeren Typ zu \textit{verengen} (Type Narrowing). Der Ausdruck \texttt{typeof f === 'string'} ist ein solcher Type Guard: Innerhalb des \texttt{if}-Zweigs weiß der Compiler, dass \texttt{f} nur noch ein \texttt{string} sein kann; im \texttt{else}-Zweig ist \texttt{f} entsprechend „alles außer \texttt{string}“ aus dem ursprünglichen Union-Typ.

\paragraph{Strukturelle Fallunterscheidung: \texttt{match} vs.\ \texttt{switch} mit Kontrollflussanalyse.}
Python nutzt Pattern Matching (\texttt{match}/\texttt{case}), um die Baumform direkt über Muster wie \texttt{('↔', g, h)} zu zerlegen. TypeScript kombiniert zunächst einen Type Guard (\texttt{typeof}) mit einer \textit{kontrollflussbasierten Typanalyse} (Control-Flow Based Type Analysis): Nach dem frühen \texttt{return} im \texttt{if}-Zweig ist im restlichen Code garantiert, dass \texttt{f} kein \texttt{string} mehr ist, wodurch Destructuring wie \texttt{const [op] = f;} typseitig zulässig wird. Anschließend wirkt \texttt{switch (op)} als zweite Verengung: Da \texttt{op} in \texttt{Formula} ein \textit{Literal-Typ} (z.\,B.\ genau \texttt{'↔'} oder \texttt{'¬'}) ist, kann der Compiler in jedem \texttt{case} die konkrete Tupel-/Array-Form von \texttt{f} ableiten.



\paragraph{Warum TypeScript nach Type Guards „mehr weiß“.}
In TypeScript sind die erlaubten Formen von \texttt{Formula} als Union aus wenigen, klaren Array-Tupelmustern modelliert (z.\,B.\ \texttt{['¬', Formula]} oder \texttt{['↔'|... , Formula, Formula]}). Nach dem Type Guard \texttt{typeof f === 'string'} reduziert sich die Menge möglicher Formen automatisch auf die nicht-string Varianten; danach reduziert \texttt{switch (op)} die Möglichkeiten weiter auf genau denjenigen Zweig, dessen Operator-Literal passt. Dadurch ist beispielsweise im \texttt{case '¬'} statisch bekannt, dass \texttt{f} genau zwei Elemente besitzt und an Position 1 eine Teilformel liegt, während im \texttt{case '↔'} (bzw.\ allgemein bei binären Operatoren) statisch bekannt ist, dass \texttt{f} drei Elemente besitzt und an Position 1 und 2 jeweils Teilformeln liegen.

\paragraph{Zentrale Unterschiede in \texttt{eliminateBiconditional}.}
In Python ist das abschließende \texttt{return None \# type: ignore} ein praktischer Hinweis darauf, dass der Typchecker die Vollständigkeit der Fallunterscheidung nicht sicher ableiten kann; in TypeScript wird die erreichbare Typpräzision hingegen durch Type Guards und die kontrollflussbasierte Verengung wesentlich stärker ausgenutzt.


\subsubsection{Negationsnormalform: \texttt{nnf} in Python vs.\ TypeScript}
Die Funktion \texttt{nnf} transformiert eine Formel in \textit{Negationsnormalform} und bildet damit die Schnittstelle zwischen den vorherigen Operator-Eliminierungen und der anschließenden \ac{KNF}-Konstruktion. % [file:2][file:3]
Der zentrale Unterschied der beiden Implementierungen liegt weniger im rekursiven Kontrollfluss, sondern in der \textit{typseitigen Spezifikation} des Ergebnisses: In TypeScript wird das Ziel explizit durch den eigenständigen Typ \texttt{NNF} modelliert, während Python auch nach der Transformation weiterhin den generischen Typ \texttt{Formula} verwendet. % [file:2][file:3]

\Needspace{7\baselineskip}
\begin{minted}{typescript}
	type NNF = Variable | ['⊤'] | ['⊥'] | ['¬', Variable] | ['∧' | '∨', NNF, NNF];
	
	export function nnf(f: Formula2): NNF {
		"Compute the negation normal form of f."
		if (typeof f === 'string') {
			return f;
		}
		const [op] = f;
		switch (op) {
			case '⊤':
			return ['⊤']
			case '⊥':
			return ['⊥'];
			case '¬': {
				const [, g] = f;
				return neg(g);
			}
			case '∧':
			case '∨': {
				const [, g, h] = f;
				return [op, nnf(g), nnf(h)];
			}
		}
	}
\end{minted}
\captionof{listing}{TypeScript: \texttt{nnf} mit Eingabetyp \texttt{Formula2} und Rückgabetyp \texttt{NNF}} % [file:2]

Der Typ \texttt{NNF} kodiert die strukturelle Invariante „Negation nur vor Variablen“ direkt im Typsystem, da negative Literale ausschließlich als \texttt{['¬', Variable]} zugelassen sind und \texttt{['¬', NNF]} gerade \textit{nicht} existiert. % [file:2]
Damit können nachfolgende Transformationsschritte (insbesondere die \ac{KNF}-Konstruktion) statisch davon ausgehen, dass sie nie einen Negationsknoten über einer zusammengesetzten Teilformel behandeln müssen. % [file:2]
Zusätzlich ist der Eingabetyp bereits \texttt{Formula2}; dadurch sind Operatoren wie \texttt{'↔'} und \texttt{'→'} in \texttt{nnf} typseitig ausgeschlossen, was den \texttt{switch}-Block auf genau die verbleibenden Fälle reduziert. % [file:2]

\Needspace{7\baselineskip}
\begin{minted}{python}
	def neg(f: Formula) -> Formula:
	return None # type: ignore
	
	def nnf(f: Formula) -> Formula:
	'Compute the negation normal form of f.'
	match f:
	case str(p):
	return p
	case ('⊤', ) | ('⊥', ):
	return f
	case ('¬', g):
	return neg(g)
	case (op, g, h):
	return (op, nnf(g), nnf(h))
	return None # type: ignore
\end{minted}
\captionof{listing}{Python: Vorwärtsdeklaration von \texttt{neg} und \texttt{nnf} mit generischem Rückgabetyp \texttt{Formula}} % [file:3]

In Python ist die Funktionalität algorithmisch äquivalent, jedoch bleibt die Rückgabe weiterhin vom Typ \texttt{Formula}, sodass die Eigenschaft „NNF-Struktur“ nicht als Typinvariante festgehalten wird. % [file:3]
Auffällig ist außerdem die \textit{Vorwärtsdeklaration} von \texttt{neg}: Da \texttt{nnf} \texttt{neg} verwendet, dieses aber im Notebook erst später definiert wird, wird zunächst ein Platzhalter deklariert, um die (optionale) Typprüfung im Notebook-Kontext zu ermöglichen. % [file:3]
Diese Hilfskonstruktion ist in der TypeScript-Version nicht erforderlich, da Funktionssignaturen und Export-Reihenfolge im Modulkontext unabhängig von der Textposition statisch verfügbar sind und der Rückgabetyp \texttt{NNF} die Zielstruktur unmittelbar festschreibt. % [file:2]
Auf die \texttt{nnf}-Transformation folgt direkt die Funktion \texttt{cnf}, die explizit eine Eingabe in Negationsnormalform voraussetzt und daraus die \ac{KNF} als „Menge von Mengen“ (Klauselmenge) konstruiert, indem sie Disjunktionen über Konjunktionen verteilt. % [file:2][file:3]
In der TypeScript-Version ist diese Vorbedingung zusätzlich in der Funktionssignatur sichtbar, da \texttt{cnf} den Typ \texttt{NNF} als Eingabe erhält und eine \texttt{CNF} zurückliefert, während Python die gleiche Annahme lediglich konzeptionell trifft, aber weiterhin über den allgemeinen Typ \texttt{Formula} typisiert. % [file:2][file:3]


\subsubsection{Triviale Klauseln und Vereinfachung: \texttt{isTrivial} und \texttt{simplify} im Vergleich}
Die Funktionen \texttt{isTrivial} und \texttt{simplify} realisieren in beiden Sprachen denselben semantischen Schritt: Triviale Klauseln (d.\,h.\ Klauseln, die ein Literal und sein Komplement enthalten) werden erkannt und aus der Klauselmenge entfernt. 
In der TypeScript-Version wird dies nun konsequent in einer funktionalen Schreibweise formuliert, während Python idiomatisch \texttt{any(...)} sowie Set-Comprehensions verwendet.

\Needspace{7\baselineskip}
\begin{minted}{typescript}
	function isTrivial(clause: Clause): boolean {
		return clause.some(
		lit => typeof lit === 'string' && clause.has(new Tuple('¬', lit))
		);
	}
\end{minted}
\captionof{listing}{TypeScript: \texttt{isTrivial} als Prädikat über \texttt{some} (funktionale Schreibweise)} % [file:5]

\Needspace{7\baselineskip}
\begin{minted}{python}
	def isTrivial(Clause: Clause) -> bool:
	return any(('¬', p) in Clause for p in Clause)
\end{minted}
\captionof{listing}{Python: \texttt{isTrivial} über \texttt{any(...)} und Generatorausdruck} % [file:3]

Der Ausdruck \texttt{clause.some(...)} ist dabei die direkte Entsprechung zu Pythons \texttt{any(...)}: Beide brechen frühzeitig ab, sobald ein Element gefunden wurde, das das Prädikat erfüllt. 
Die zusätzliche Bedingung \texttt{typeof lit === 'string'} ist in TypeScript erforderlich, weil \texttt{Literal} als Union-Typ sowohl positive Literale (Variablen als Strings) als auch negative Literale (Tupelstruktur) zulässt und die Komplementprüfung hier bewusst nur für die positive Richtung \(p \mapsto \neg p\) durchgeführt wird.
Genau diese „einseitige“ Prüfung ist auch in Python implizit enthalten: Für negative Literale ist \texttt{p} kein Variablenname, sondern selbst ein Tupel, weshalb \texttt{('¬', p)} dann strukturell nicht als Komplement im Sinne eines Literals passt und die Mitgliedschaftsprüfung fehlschlägt.

\Needspace{7\baselineskip}
\begin{minted}{typescript}
	function simplify(clauses: CNF): CNF {
		return clauses.filter(c => !isTrivial(c));
	}
\end{minted}
\captionof{listing}{TypeScript: \texttt{simplify} durch Filtern der Klauselmenge} % [file:5]

\Needspace{7\baselineskip}
\begin{minted}{python}
	def simplify(Clauses: set[Clause]) -> set[Clause]:
	return { C for C in Clauses if not isTrivial(C) }
\end{minted}
\captionof{listing}{Python: \texttt{simplify} als Set-Comprehension} % [file:3]

Auch \texttt{filter} entspricht semantisch der Python-Set-Comprehension: In beiden Fällen wird eine neue Menge konstruiert, die exakt diejenigen Klauseln enthält, für die das Prädikat \texttt{not isTrivial(...)} gilt.
In TypeScript ist hierbei zentral, dass die verwendete Mengenstruktur diese funktionalen Operationen (u.\,a.\ \texttt{some} und \texttt{filter}) bereitstellt und zugleich die Mitgliedschaftsprüfung \texttt{has} auf wertbasierter Gleichheit für verschachtelte Tupel stützt. % [file:5]





\subsubsection{Gesamtpipeline und Ausgabetests: \texttt{normalize}, \texttt{test} und \texttt{prettify}}
Die Funktion \texttt{normalize} fasst die zuvor eingeführten Transformationsschritte zu einer linearen Pipeline zusammen: Zunächst werden \texttt{↔} und \texttt{→} eliminiert, anschließend wird die Negationsnormalform berechnet, daraus die \ac{KNF} konstruiert und abschließend vereinfacht. % [file:2][file:3]
Damit bildet \texttt{normalize} den zentralen Einstiegspunkt für die algorithmische Verarbeitung, da alle Zwischenresultate in einer klar definierten Reihenfolge erzeugt werden. % [file:2][file:3]

\Needspace{7\baselineskip}

		const n1 = eliminateBiconditional(f);
		const n2 = eliminateConditional(n1);
		const n3 = nnf(n2);
		const n4 = cnf(n3);
		return simplify(n4);
	}
